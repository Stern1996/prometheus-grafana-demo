# 画廊图素材

这三张图是给 Fiverr / Upwork gig 用的。全部来自**你自己的演示环境**，不含任何公司数据。

---

## 主图（按 Fiverr 画廊顺序排）

### `01-dashboard.png` — Grafana 仪表盘 ⭐ 最重要

- 1920×1220
- 拿到这张图的时刻：系统**当前健康**（错误率 1.25%、p95 229ms、worker 22.3%、缓存命中 96.8%），但**过去 10 分钟里有两次故障窗口**清晰可见
- 为什么这样选：既显示系统运行良好，又证明这套监控能抓到问题。如果只截一张全绿的图，客户看不出你的价值；只截一张全红的图，又像在展示一个坏掉的系统

> 这张决定点击率。Fiverr 的曝光几乎完全由点击率驱动，值得多截几个时间点慢慢挑。

### `02-architecture.png` — 架构图

- 2560×1520（2× 渲染，可缩放）
- 源文件：`src/architecture.html`，改文字后重新渲染即可
- 作用：一眼说明你理解整套数据流，而不只是会装软件

### `03-alert-rules.png` — 告警规则

- 3000×1544（2× 渲染）
- 来源：Prometheus 的 `/rules?theme=dark`（深色模式，和另外两张统一）
- 作用：证明你配了**告警**，不只是画了好看的图。7 条规则分 3 组，每条都带 `action` 注解

## 这些图是怎么做出来的（可复现）

```
demo-app/app.py        → 真实的 HTTP 服务，指标来自它自己的请求处理
demo-app/loadgen.py    → 真实压测流量，约 18 req/s
prometheus/            → 抓取 + 7 条告警规则
dashboards/*.json      → 仪表盘，由 scripts/build_dashboard.py 生成
scripts/screenshot.ps1 → headless Chrome 截图
gallery/src/*.html     → 架构图源文件
```

重新生成：见 `../SCREENSHOTS.md`。

---

## 一句重要的话：这些不是假数据

演示服务 `app.py` 输出的是**它自己真实测量的结果**——请求数来自真实处理的 HTTP 请求，延迟直方图来自真实的 `time.perf_counter()` 计时，故障窗口是它真的在返回 500。

所以当客户问"这个仪表盘是真的吗"，你可以坦然回答：

> 这是我自己的演示环境，你可以 clone 下来跑，五分钟就能看到同样的图。

**这比任何解释都有说服力。** 而且它同时证明了一件更重要的事：你不依赖公司的现成环境，也能从零把东西搭起来。
